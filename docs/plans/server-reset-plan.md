记录在 `test-results/blank-canvas/2026-11-06T21-43-31-607Z-pixelShots-canvas.json`：

- **不是一开始就断，是卡住以后才断。** 页面 13:42:01.965 开始打开：
  - `react`、CSS、`three` 三个文件各用了 **10.1 到 10.2 秒**才到。平时整个页面 1.35 秒就打开了（probe 中位数）。三个文件最后都是 200，收完了；
  - 主文件 `index-BxCOFJFQ.js` 收到 **164,067 字节**（压缩后的大小，全文约 209 KB）以后就没有下文，到 **29.1 秒**时连接被断开（`ERR_CONNECTION_RESET`）；
  - 页面的 `load` 事件在 29.1 秒，`#root` 是空的，没有页面错误，没有长任务，没有 WebGL 记录。
- **服务器的输出**这次写进了文件（`serve-new.log`），只有启动时那两行，断开时什么也没说。

### 1.4 这些证据说明什么，不说明什么

- **不需要三个浏览器同时开。** 以前的记录里，断连只出现在 probe"三个浏览器同时开"的那几轮，所以登记时写的是"可能是同时开太多"。今天一个浏览器、一页一页开，也断了。
- **断连是"卡住"的结尾。** 卡住时整页的文件都慢（10 秒），主文件卡得最久，最后被断开。probe 那两次"`page.goto` 超过 90 秒"是同一种卡住，只是没断：本站文件各用了 70–90 秒（decisions.md，probe 那一段）。所以要数的不只是断连，**卡住**（本站的某个文件超过 5 秒才到）也要数。卡住比断连多，比较好量。
- 已知的 5 次断连，断的**都是主文件**：
  - 第 101 轮第一步那次没有记录，它是在装记录工具之前；
  - probe 1 次、端头 2 次、今天 1 次，都写着是主文件。
- **还不知道是谁卡住的**，可能是：
  - 服务器那个 Node 进程卡住了；
  - Vite 的边送边压缩卡住了；
  - 本机的网络层（含防病毒的网络检查）卡住了；
  - 浏览器的网络进程卡住了；
  - 整台电脑那一刻忙不过来。
  - 现有的记录分不出这几种：服务器的输出被丢掉了，浏览器那边只看得到结果。
- 也不知道是谁发的断开。Node 的 5 秒空闲关闭，在时间上对不上：断开时连接正在传数据，不是空闲的。

## 2. 五种做法和代价（用今天的证据重新看过）

**甲：先找原因**

- 做法：
  - 服务器改用 Vite 自己的 `preview()` 函数，在 `tests/globalSetup.ts` 里启动，不再另开进程。这样可以在服务器上挂记录：
    - 每个请求的开始和结束时间、送了多少字节；
    - 连接的开、关和出错（`ECONNRESET` 之类）；
    - Node 主线程有没有被卡住（`perf_hooks.monitorEventLoopDelay`）。
    - 都写进一个文件。
  - 另外开一个"心跳"：一个独立的 Node 小程序，每 250 毫秒向服务器要一个小文件，记下多久回来。服务器卡住时心跳也会慢；服务器正常而浏览器卡住时，心跳不受影响。
  - 浏览器那边加 Chromium 自己的网络日志（`--log-net-log`）：哪个连接、是新开的还是用旧的、断之前收了多少。
  - 用拍照的开法反复开页面，量出断连和卡住的次数（见第 4 节）。
- 代价：
  - 本身不修任何东西；
  - 要跑一次大约 75–90 分钟的循环；
  - `globalSetup.ts` 的启动方式会变（同样是 `vite preview` 的代码，只是在测试进程里跑）；
  - 网络日志很大，只在这个循环里开，不进全套测试。

**乙：只为这一种情况重开一次页面**

- 做法：主文件从 `localhost` 来、报 `ERR_CONNECTION_RESET`、`#root` 是空的，就重开一次，每次重开都记下来，最后报数。
- 代价：
  - "红就是红"这条规矩要开一个写明的例外，要你批；
  - 真有一个长得一样的毛病，会被放过一次；
  - **按今天的证据还管不全**：卡住但没断的（probe 那两次 90 秒）不报这个错，照样会红，除非把条件放宽到"本站文件超过多少秒"。放得越宽，放过的越多。

**丙：测试换一个服务器**

- 做法：在测试里用 Node 的 `http` 自己写一个小服务器（不加新依赖），代替 `vite preview`。
  - 不边送边压缩；
  - 文件开跑时一次读进内存，以后不碰硬盘。
- 代价：
  - 要和 `vite preview` 一样地送文件：路径前缀、文件类型、找不到时回 `index.html`。这几样都要有测试守着；
  - 多一个自己维护的服务器；
  - **如果卡住的不是服务器**（网络层、浏览器或整台电脑），换了也没用。甲能先回答是不是服务器的问题。

**丁：浏览器和硬盘之间不经过服务器**

- 做法：浏览器要本站文件时，由 Playwright 直接从 `dist/` 读出来回答（`context.route`），地址不变。
- 代价：
  - 测试不再走真正的 HTTP：响应头、缓存、压缩都不经过；
  - 每个测试的浏览器上下文都要接上，probe 和拍照脚本也要接，不然它们测的是另一条路；
  - 接错了，会出一个只在测试里有、看起来却像网页的毛病；
  - 如果卡住的是浏览器自己或整台电脑，它也没用。

**戊：不管，照现在这样，红了就重跑**

- 代价：
  - 一次全套测试大约 86 分钟（2026-11-06 量的是 5,173 秒），按 90 分钟排；
  - 装上记录工具以来跑完的 4 次全套测试里，有 1 次因为这个白跑了 68 分钟；
  - 拍照每 300 次左右的开页面断一次，断了那一组作废重拍，一组 9 分钟；
  - 这一项登记的就是这种代价："已经让全套测试白跑好几次"。

## 3. 我的建议：先做甲，再在丙和丁之间选

**先做甲**，限定一次循环，结果给你看了再选下一步。为什么：

- 今天的证据把问题从"断连"变成了"卡住，有时以断连收尾"。乙只管断连，管不到卡住，而且要给"红就是红"开例外。
- 丙和丁各自只对一种原因有用：
  - 丙只在服务器卡住时有用；
  - 丁在服务器或本机网络层卡住时有用，但它让测试不再走 HTTP；
  - 浏览器或整台电脑卡住时，两个都没用。
  - 不先知道是哪一种，选哪个都是猜。
- 甲很小，改的只有测试环境：`globalSetup.ts` 的启动方式，加一个心跳和一个循环脚本。它的循环本身就是第 4 节要的"改前"数字，不会白做。

**甲做完以后**，按结果建议：

- 服务器那个 Node 进程或压缩卡住（心跳也慢，或主线程被卡住）→ **丙**；
- 服务器正常，卡在本机网络层（心跳正常，浏览器的网络日志显示连接卡住）→ **丁**；
- 服务器和网络都正常，卡在浏览器或整台电脑 → 丙和丁都没用，回来和你商量乙或戊；
- 循环里一次都没出现 → 再跑一次。还是没有，就照戊，等全套测试里再出现时，用甲留下的记录来看。

## 4. 怎么证明修好了

**数什么**

- **断连**：页面自己的文件报 `ERR_CONNECTION_RESET` 或 `ERR_CONNECTION_CLOSED`。
- **卡住**：页面自己的某个文件超过 5 秒才到。平时整页 1.35 秒（probe 中位数），今天卡住时是 10 秒。
- **画不出来**：60 秒没有画布，或 `page.goto` 超过 90 秒。

**怎么开页面**

- 照拍照的开法：一个浏览器，每次新开一个上下文，一页一页地开，等画布出来，再等 2.5 秒，然后关掉。桌面和手机各一半，和拍照一样。
- 服务器就是全套测试启动的那一个，启动方式也一样。
- 每次打开都记下每个本站文件用了多少时间，所以卡住了也数得到，不用等它断。

**跑多少次**

- 按过去的数字，拍照大约每 300 次断一次（1.2 节：594 次断 2 次）。卡住的次数没量过，甲的循环会量出来。
- **改前**：1,000 次。照过去的比例，应该断 3 次左右，卡住的次数更多。
  - 这 1,000 次就是甲的循环，同时带着服务器记录、心跳和网络日志。
  - 一次大约 4–5 秒（1.35 秒打开，2.5 秒等待，加开关），1,000 次约 75 分钟，按 90 分钟排。
  - 跑之前读电源设置，跑之后查系统日志，中间有待机就作废，和全套测试一样。
- **改后**：同样的 1,000 次，同样的开法和机器。
- **怎么才算修好**：改前断连加卡住至少 3 次，改后断连 0 次、卡住 0 次。
  - 如果修了等于没修，比例还是每 300 次一次，那么 1,000 次一次都不出现的可能大约是 4%。
  - 改前要是不到 3 次，说明这个开法引不出来，次数加到 2,000 再比。
- **再加全套测试**：改后接下来的 3 次全套测试，一次断连或卡住都没有。全套测试会在 `test-results/blank-canvas/` 留下记录。
  - 甲还会让测试环境数出每次全套测试开了多少次页面，以后可以按开页面的次数比，不只按跑了几次全套测试比。
- 每个数字都写出处：循环的输出文件、服务器记录、系统日志的时间段，和这次一样写进 decisions.md。

## 5. 只改测试环境，不碰网页

- **网页本身**（`src/`、`index.html`、`public/`、`data/`）每一种做法都不碰。上线的文件逐字节不变：改完以后主文件名会因为提交号变，其他文件都和 `664b570` 的一样，上线核对会照常列出来。
- 各种做法会碰的文件：
  - 甲：`tests/globalSetup.ts`（启动方式、服务器记录）；新的心跳和循环脚本放在 `scripts/` 下。
  - 乙：`scripts/pageWatch.mjs`。
  - 丙：`tests/globalSetup.ts`，加一个新的测试服务器文件和它的测试。
  - 丁：`tests/` 下每个开页面的地方，加 `scripts/pixelShots.mjs`、`scripts/blankCanvasProbe.mjs`。
- 拍照用的服务器（每轮在别的端口开的 `vite preview`）现在不经过 `globalSetup.ts`。甲的服务器记录要不要也接到拍照上，在第 6 节问你。

## 7. Leo 的回答（2026-11-06）

> 「计划确认，做甲。」

1. **服务器不搬进测试进程。** 原话：「写一个独立的启动脚本（比如 scripts/previewServer.mjs），里面调用同样的 preview()，挂上请求、连接、出错和主线程卡顿的记录，仍然作为单独的进程启动，输出写进文件。」
   - 理由，原话：「搬进测试进程，服务器就和测试自己的工作共用一个主线程，量到的"卡住"可能是搬家造成的，也可能把原来的问题盖住；而且这个改动会永久留在全套测试里。」
   - `globalSetup.ts` 和拍照脚本都改用这个启动脚本。
   - 所以第 2 节甲里"在 `tests/globalSetup.ts` 里启动，不再另开进程"那一句作废，以这一条为准。
2. **改前跑 1,000 次**；不到 3 次，照计划加到 2,000 次。
3. **修好的标准照第 4 节。** 另外，报告里写出每个本站文件的用时分布：一般用多久、最慢 1% 用多久。改前改后都写，不只报次数。
4. **拍照用的服务器也接上记录**，用第 1 条那个启动脚本。
5. **再补一项记录**：循环期间用 Windows 的 `typeperf` 每秒记一次 CPU 和硬盘的忙闲，写进一个文件。原话：「这样"整台电脑忙不过来"能直接看到，不用靠排除来推。」

## 8. 这一轮的顺序

3. **结果给 Leo 看**：
   - 断连、卡住、画不出来各几次；
